## 三、本轮新发现

### 阻断（2 项）

**N1｜TLS pin 实现路径技术不可达——四方独立验证收敛。**
- 〔主评实测〕Windows curl 8.21.0（Schannel）+ Git Bash curl 8.23.0（Schannel）+ openssl 3.5.9 自签证书回环实测：`--pinnedpubkey` **不带** `-k`/`--cacert` → **exit 60 `SEC_E_UNTRUSTED_ROOT`**（链校验先行失败，pin 未执行）；〔证据轴独立实测〕同结果，且 `--cacert+pin` → exit 0 成功、`-k`+错误 pin → exit 90（pin 在 `-k` 下仍强校验）；〔风险轴外验〕curl 官方文档语义「链验证通过**且**公钥匹配」二者并存、pin 不豁免链校验。
- 后果：设计 §7.4.3 L307「仅 pin、禁 `-k`」在自签场景必败——**AC-I03（干净环境安装成功）与 AC-I09（pin 校验）无法同时满足**；§5.2/§5.3 探针恰好漏掉「pin 正确但无 trust anchor」这一唯一必现场景。
- 平台矩阵缺口〔风险轴外验+主评〕：`--pinnedpubkey` 需 curl ≥7.44（sha256// 形式）、`--header @file` 需 ≥7.55；**el7 stock curl 7.29 两者皆无**——需求包 L36 服务机为 el7，目标机同质概率高，则 el7 目标机整类出局，设计 L267 平台矩阵只有 os/arch、无 curl 版本/后端门槛。
- **修正建议（推荐 a+c）**：a) `--cacert <自签证书> --pinnedpubkey` 双锚（自签作自身锚通过链校验，pin 提供端到端公钥认证与 cacert 被篡改的兜底，不违反 AC-I09，实测可行）；c) 平台矩阵登记 curl ≥7.55 门槛与 el7 不支持的处理指引。备选 b) 修订 REQ-I05/AC-I09 措辞区分「裸 -k（禁）」与「-k+pin（公钥校验完整执行）」——须主人重开决策（并登记 CVE-2026-80230 的 ≥8.22 门槛）。

**N2｜yufu↔服务端认证传递矛盾——AC-M06 按现文无法验收。**
- 设计 L217 写操作条件「管理监听可达 +（yufu 身份头**或**本机 CLI 凭据）」：服务端无法区分「yufu 反代注入的头」与「直连 8788 伪造的头」（同为 loopback TCP），本机直连+伪造头即满足条件——与 L132 探针「伪造 X-Auth-Username 不获得签发权限」及 AC-M06（L128）「仅带头不构成认证」**直接矛盾**。
- 对策（三选一，UNIX socket 可同时关 N3）：HMAC 共享秘密头（yufu 签、服务端验）/ 管理监听改 UNIX socket（文件属主门禁）/ 写操作强制本机 CLI 凭据（去掉「或」分支）；AC-M06 补「本机进程直连伪造头」探针场景。

## 四、主评实测记录（lead，2026-10-29 本机）

环境：Windows curl 8.21.0（Schannel）、Git Bash curl 8.23.0（Schannel Debug 构建）、openssl 3.5.9；自签证书（SAN=localhost/127.0.0.1）+ `openssl s_server` 回环，材料即建即删。

| 场景 | 结果 |
|---|---|
| pin-only（无 -k 无 --cacert，即设计 L307 方案） | **exit 60** SEC_E_UNTRUSTED_ROOT（两版本 curl 一致） |
| `-k` + 正确 pin | exit 0（TLS 通过） |
| `-k` + **错误** pin | **exit 90** `public key does not match pinned public key`（pin 在 -k 下强制生效） |
| 裸 `-k`（无 pin） | exit 0（即 AC-I09 所禁的裸奔路径） |
| `--cacert` + pin | 证据轴独立实测 exit 0（主评首轮因证书未生成报 usage error，以证据轴实测为准） |

OpenSSL 后端行为：未本机实测（本机 curl 均为 Schannel）；按 curl 官方文档语义推断同样链校验先行失败——**建议列入 §5.3 目标平台探针实测项**。
