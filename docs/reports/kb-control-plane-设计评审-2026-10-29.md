### 轴 2：证据回源轴（evidence-auditor）

**A. §3 九行断言核对**：A1/A2/A3/A5/A6/A7/A8/A9 八行**属实且行号精确**（含 A7「grep branch_protection|/hooks 全 scripts 目录 0 命中」的否定性验证）；A4 内容属实但**行号超界**（kb-registry.mjs 全文仅 103 行，引用 89-118 超出文件末尾，一次性码证据实际在 35-87 行，应引约 35-103）。

**B. §0「改哪里」核对**：四个文件角色属实；「不新建第二个常驻服务」与现状相符（install-enroll-service.sh 只部署一个 daemon）。

**C. 可行性断言亲查（本轴增量价值）**：
- C1「升级→现有升级路径保留数据」**半有支撑**：保留 ~/.omo/home 有代码（install.sh:2 头注释、:163、:496-507）；但「检测既有安装拒绝静默覆盖」**无代码**——install.sh 无 ~/.omo 既有安装守卫，重复执行=幂等放行（仅 :219-221 对「启动器文件非本产品」拒绝）。该检测是包装脚本全新增职责，设计低估为一行描述。
- C2 manifest 与现有制品形态**大体一致、两处新账**：现状单一 tar.gz+旁车 .sha256（bootstrap.sh:148-150）、**无平台矩阵**（os/arch 是净新增建模，平台不符要到 install.sh:120 试运行才暴露）；sha256 校验需从「旁车+sha256sum -c」改为「manifest 内嵌对比」，包装脚本适配点设计未列。
- C3 安装令牌模式**可落位**：现有兑换链（kb-enroll.ts:52-71→POST /enroll:150→kb-credential.ts:98-104→git store→自证）扩展点存在；客户端 enroll() 端点**硬编码 /enroll 且无 Bearer 头**（kb-enroll.ts:150），`--install-token` 模式需参数化端点+鉴权头（小改）；服务端 /install/enroll 可复用 kb-gitea.mjs 同款链（enroll-server:469-509）。
- C4 rotate/revoke 复用 ops-kb-provision 语义**相符**（ops-kb-provision.mjs:111-250，CLI 与服务端共用 kb-gitea/kb-registry）。
- C5 配置写回链路**与现状一致**（校验 kb-ui-config:57-70→原子写 :89-104→预检 enroll-server:133-160 进程内→重启接力 :332-356/:398-404）。
- C6 §7.6「现有 API」标注**属实无虚标**（/ui/api/config GET/POST 在 :555-556；其余新 API 确不存在）。

【重要发现】① A4 行号超界；② 「拒绝静默覆盖」无代码支撑（同 C1）；③ platforms 矩阵是净新增（同 C2）；④ **重启接力 drop 集缺口**：successorArgs drop 集（enroll-server:335）不含 lint-mode/main-branch/webhook-secret——§7.3 扩白名单后，任何以显式 argv 传这三键的部署，UI 改 config.env 会被旧 argv 压制（:93-99 显式参数优先），实现时须同步扩 drop 集，设计未提及；⑤ 评审环境读取层存在秘密脱敏（enroll-server:483 显示 `randomPassword`，交叉验证表明是输出层替换而非仓库缺陷，标「未核实原文」）；⑥ 现有 /ui/api/state、/ui/api/code 未出现在 §7.6 API 草案（概览页与签码在新信息架构有页面无 API 条目）；⑦ WEBHOOK_SECRET 不在 SECRET_KEYS（kb-ui-config:30），仅靠 :122 正则兜底掩码，扩 schema 时宜显式入列。

### 轴 3：风险与安全轴（risk-security-reviewer）

【阻断】
- **RSK-B1｜TLS 信任链断裂：AC-I03 在现状自签前提下不可达。** 【验证】install-enroll-service.sh:5,262 服务端 TLS 默认自签；:455,470 现状兜底是实例侧 `--allow-insecure-tls`。【文档】设计 §7.4.3:288-292 示例命令无 -k 也无 CA 固定——干净目标机执行必因证书验证失败退出；需求包:45 一期待确认 #2（迁 yufu 合法证书）未清，设计稿未再登记。【推测】若实践改用 -k，MITM 可自洽替换整链（假 manifest+假制品+匹配哈希），/install/enroll 响应中的 KB bot 凭据可被截获——违反需求包:119「不以关闭证书验证换取便利」。**对策：设计内明确信任引导方案（证书指纹带外核验固定，或拍板迁 yufu），并将 -k 路径从推荐命令移除。**
- **RSK-B2｜管理面信任头等价可伪造，新增签发类 API 放大一期遗留风险。** 【验证】kb-auth.mjs:14-19 只查头存在不验来源；install-enroll-service.sh:10 部署示例 `--host 0.0.0.0`。【文档】设计 §7.6 将 secret 轮换、安装令牌签发、实例凭据操作全挂 /ui/api 下，而生成安装命令必须开 UI（§7.2 默认 off→实际常开）。任意网络可达者伪造身份头即获令牌签发+凭据兑换入口，等价无认证管理入口，违反需求包:119 底线；§4:101 把「沿用身份头」当对策而未登记可伪造风险。**对策：管理 API 监听分离（127.0.0.1+yufu 反代强制）或身份头带签名校验；风险入 §4，作为签发类 API 上线前置条件。**

【重要】I1 制品缓存写入路径缺失（§7.6 无 installers/artifacts 写入接口，installers.json 由谁经什么权限写入未交代）；I2 manifest sha256 担保链未闭环（代理上游模式下哈希若取自上游元数据，上游被劫持时假制品+假哈希同链通过；script.sha256 校验主体/时机未说明）；I3 webhook secret 轮换与 Gitea 侧配置耦合（【验证】enroll-server:181-184 验签失败即 401→kb-lint 停摆=门禁静默失效；rotate 与 gate/apply 顺序约束未写）；I4 安装令牌经 curl argv 的 ps 暴露（建议 `curl --header @<0600文件>`）；I5 /install/artifacts/:name 无输入校验设计（路径穿越面）；I6 状态机触发条件与并发写不完备（issued→active/→completed 触发未定义；install-tokens.json/instances.json 读-改-写竞态，tmp+rename 不解决丢失更新）；I7 安装令牌熵/格式/限流未登记（现状 enroll 码为 randomBytes(24)=192bit，新令牌未登记同等要求）。

【建议】S1 未绑定 device 时 hostname 可伪造污染实例记录（建议默认绑定、以 installId 为唯一键）；S2 脚本重试策略与服务重启窗口期 in-flight 会话恢复未明确；S3 验证盲区（§5.2 缺探针：令牌爆破/限流、自签证书验证失败、installers.json 篡改/缓存投毒、report 洪泛、:name 穿越）。

【通过项】令牌与兑换码分离不混用（:263）；令牌只存哈希、明文仅返回一次、不写日志/审计明文（:246,267）；一次性+TTL+可吊销+可选设备绑定（:261-264）；目标机不接收管理员秘密、无反向 SSH（§7.8:396）；AC-I07 四子项（脚本/命令/响应/日志不含可复用秘密、区分获取与接入、不凭下载推断在线）设计层面均达标；拒绝静默覆盖+升级保留数据（:276-278）；secret 不回显（:201,211）；管理员凭据/registry 路径不可经 UI 改（:212）；无制品明确失败不回退旧脚本（§2:70）。
