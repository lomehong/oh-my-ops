## 一、残留风险是什么（事实，非推断）

| 项 | 内容 |
|---|---|
| **场景** | 交互态（`ctx.hasUI === true`）+ 操作者**显式** `--approval-mode yolo` + 未预授权 |
| **后果** | `exec` 档操作会被执行（①-b 无人值守兜底层**只在 `!hasUI` 时生效**，交互态信任平台审批） |
| **范围** | 仅影响「非生产目标 + 操作者主动关闭审批」的组合；**生产目标由 `policy:"deny"` 独立兜住**（yolo 下仍拒，X3/X8 实证） |
| **自检限制** | 扩展 API 读不到 `approvalMode`（X14 实测：`pi` 自有成员无 settings 访问器）——**扩展无法在运行时自检该模式** |

## 二、可选处置口径（三选一或组合）

| 方案 | 做法 | 代价 | 效果 |
|---|---|---|---|
| **A. 接受 + 部署规范约束**（设计现状） | 不写代码；在部署规范与 README 中禁止 yolo；生产目标靠 policy:deny 兜底 | 零成本 | 残留仍存在，依赖「人不犯错 + 生产有 policy.deny」 |
| **B. 交互态也叠加兜底层** | ①-b 改为「无论 hasUI，未预授权 → 拒绝」，把「批准」完全交给预授权文件（P2/P3） | 交互态体验变差（每次高危都要写令牌，不能再靠平台弹窗批准） | 消除 RR-1；安全语义单一化 |
| **C. 交互态"二次确认"兜底** | ①-b 在 hasUI 时改为：`ctx.ui.confirm(高危动作)` 显式询问主人，拒绝则 `{block:true}` | 每次高危多一次点击；`tool_call` 30s 上限内需完成交互（O6） | RR-1 消除且保留交互便利；**风险**：30s 超时会 fail-closed（block），体验需评估 |

## 三、评审方倾向（不作为结论）

倾向 **C 为主 + A 兜底**：

- C 在交互态把「显式 yolo 静默放行」变成「显式确认」，符合本项目一贯的**降级收敛保守侧**与**不得静默放行**纪律；
- 平台弹窗（approval 门）此时仍生效，C 只是**叠加**而非替代；
- 30s 上限（O6）下 `ctx.ui.confirm` 若超时会 fail-closed（block）——**方向正确**（拒绝优于放行），但需在 P3 实施时实测确认交互耗时；
- 无论选哪个，**部署规范禁止 yolo** 都应保留（纵深防御第一层）。

## 四、需要的决策

请主人选择：

1. **接受现状（A）**；或
2. **交互态也拒绝未预授权（B）**；或
3. **交互态二次确认兜底（C）**——评审方倾向；或
4. **其他口径**（请说明）。

决策后：由 OpsPi 实施方（omp 侧会话）落到 §7.4/§7.8 与 §5 契约测试（新增「交互态未预授权」断言项），并在 §4 残留风险表更新为「已处置」或保留并注明依据。
