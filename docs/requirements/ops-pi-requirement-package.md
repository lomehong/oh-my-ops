## 0. 一句话需求

**基于 oh-my-pi（omp）扩展**实现一套运维智能体：无人值守下完成只读巡检，并对「指定服务」执行重启；高危敏感操作须 Owner 明示批准；全过程留可追溯审计。安全与效率机制尽量复用 omp 原生能力（审批子系统、受管定时器、输出 spill），不自造平行机制。

> **平台决策沿革（2026-09-12，以最新为准）**：最初要求「基于上游 pi 封装」→ 经能力矩阵对照发现 pi 扩展平台偏简陋（无审批子系统、无受管定时器、无输出 spill，schema 侧标 legacy）→ **主人定稿：运行时目标 = omp**。

## 1. 可验收目标（Acceptance）

| # | 目标 | 验收判据（可观测、可复跑） |
|---|---|---|
| A0 | **基于 omp 平台能力**（不造平行机制） | 扩展在 omp 18.x 上加载并注册全部 `ops_*`；启动期平台能力校验通过（`pi.zod`/`ctx.setInterval`/`approval` 字段被宿主识别/`pi.appendEntry` 等，见方案 §7.2）；安全机制由宿主 `approval` + 内容硬拒 + 目标策略三处构成，**无自研审批 GUI 或独立权限引擎** |
| A1 | 无人值守只读巡检 | `omp -p "巡检 web-01"` 无需任何人工交互即可完成；产出聚合报告（ok/warn/critical 计数 + 异常项明细）；进程退出码 0 |
| A2 | 对「指定服务」执行重启 | 仅当「主机 + 服务名」同时命中 Owner 允许清单时，无人值守下 `ops_service(restart)` 放行；未命中则被拒绝并给出明确原因 |
| A3 | 高危敏感操作须 Owner 明示批准 | 生产变更 / 数据破坏 / 凭据写入等，在无人值守下**默认失败**；仅在 Owner 已签发有效授权（配置允许项或带时效的批准令牌）时放行 |
| A4 | 全过程留审计 | 每一次 `ops_*` 调用（含被拒绝的）在会话分支留下 `ops_audit` 条目，含工具名、输入、结果状态、时间戳、授权来源；**拒绝条目须可辨层级**（`layer` 字段：`guard-content`/`guard-*`/`execute-revalidation`/`end`）；当前分支内可读 |
| A5 | 不依赖任何单点外部增强 | Yuyi 适配器 / 御符 / vault 任一缺席时，A1–A4 仍成立（外部增强缺席只收窄能力、显式提示、可恢复，且收敛到保守侧）。**平台能力缺失则为硬失败（拒绝启动），与外部增强降级区别对待** |
| A6 | **入参完整性（抗篡改）** | 共载扩展改写 `ops_*` 入参时（**四种方向**），**不得执行改写后的命令**：伪造为已授权值 → ①-a 首评在钩子前短路；改成未授权值 → ①-a 复评；仅改命令内容 → ③ execute 复核；注册在兜底之前 → ①-b。**前提**：预授权以 `defaultDeny` 表达在**审批层**、`authorizedExec` 为**纯函数**、③ 重算**全部**校验维度。四条均可复跑（方案 §5 负测 ⑨） |

## 2. 范围（Scope）

**在范围内**

- L1 `@ops-pi/core`：运维原子能力（Shell / SSH / Docker / K8s / Process / Log / File / Health / Vault），纯 Node.js，**不依赖 omp**，可独立 CLI 测试；
- L2 `@ops-pi/extension`：**omp 扩展**（规范导入 `@oh-my-pi/pi-coding-agent`；schema 用注入的 `pi.zod`），注册 `ops_*` 工具（含 `approval` 档与 `loadMode:"essential"`）+ 内容硬拒 + 目标策略 + 审计；斜杠命令（只读）；
- L3 编排模式：巡检 / 诊断 / 自愈 / 部署，以提示词 + 事件 + 工具编排表达；
- 安全模型：三层分工（宿主原生审批 → 内容级硬拒 → 工具内目标策略）+ Owner 预授权；
- 沙箱部署形态（容器 + 挂载/网络策略）。

**范围外**

- 调用方身份鉴权（归 Yuyi 插件自治；ops-pi 用目标导向 defaultDeny，不依赖身份）；
- 跨设备协同（宿主无对应物，如实声明能力边界，由主人中转）；
- 自研 Agent 循环 / 模型路由 / 会话管理（复用宿主）；
- 其他 harness（pi 上游 / dsh 等）的适配——本版**单平台目标 = omp**；如需移植，按矩阵 §2 另立评估。

## 3. 不做项（Explicit Non-Goals）

| # | 不做 | 原因 |
|---|---|---|
| N1 | 不自研与宿主平行的审批子系统（无自研权限引擎/独立确认 GUI） | 平台决策：omp 原生 `approval`/`approvalMode`/`tools.approval.*`/`tool_approval_*` 事件已覆盖，且判定顺序支持 `policy:"allow"\|"deny"` 表达目标级授权 |
| N2 | 不在扩展内 `import` 第三方内部类以「复用」其实例 | 宿主无跨扩展状态共享；扩展按 per-entry 独立加载，import 得到第二个实例（第二个 Hub 连接） |
| N3 | 不自研跨 Agent 通信（bridge / ReplyLoop / 闸门 / 主从锁） | 共载 Yuyi 官方适配器（§4.6 决策） |
| N4 | 不使用 `input` 事件做关键逻辑（场景过滤等） | 该层非关键路径且契约面易变；场景引导改由 `before_agent_start` 提示词承担 |
| N5 | 不在 `tool_call` hook 内做**长时间**交互等待 | 宿主管限额 30s，超时 fail-closed 会误判为超时并阻断；该层只做同步判定 |
| N6 | 不用斜杠命令直调 L1 执行危险动作 | 命令路径不产生 `tool_call`/`tool_result`，会绕过审批与审计 |
| N7 | 不在扩展工厂内启动后台资源（定时器/进程/socket/文件监视） | 工厂可能在不启动会话的调用中运行；须在 `session_start` 后启动，`ctx.setInterval` 自动清理 |
| N8 | 不自研输出截断 | 宿主已集中 spill 到 artifact 并把内联换 head+tail；自截断会导致 artifact 只存到截断后文本（丢数据） |
| N9 | 不把宿主平台能力当「可选增强」降级 | 平台能力（审批/schema/定时器）是安全前提，缺失必须硬失败；只有 Yuyi/御符/vault 等外部件才走降级 |

## 4. 假设（Assumptions，未经确认即失效）

| # | 假设 | 依据 | 若不成立的影响 |
|---|---|---|---|
| H1 | **运行时平台 = oh-my-pi（omp 18.x）**，单一目标 | 主人 2026-09-12 决策（pi 平台能力简陋）；能力矩阵 | 若需支持其他 harness，需按矩阵 §2 另立评估与适配 |
| H2 | omp 的原生审批语义稳定：`approval` 省略默认 `"exec"`、`read` 档在三模式均放行、`policy:"allow"\|"deny"` 最优先解析、`approvalMode` 三值 | O2/O3 + 实测 X1–X3（omp 18.1.18） | 安全门语义失效；须靠方案 §7.2 平台探针在启动期发现 |
| H3 | Owner 可通过编辑配置/令牌文件表达「明示批准」 | 无人值守无 UI 时宿主审批硬失败（O4）；故必须离线预授权 | A3 需改依赖异步批准通道（**注**：原指向 B1 的路径已撤销，身份归 Yuyi 插件自治） |
| H4 | 「指定服务」清单由 Owner 维护，规模有限（数十项） | 运维常识 | 需引入配置分发机制 |
| H5 | omp 迭代不会移除 `approval`/`loadMode`/spill 等本方案依赖的能力 | 无版本承诺文档（U2） | 启动期探针会先失败；需随 omp 升级按 §5 回归清单复核 |
