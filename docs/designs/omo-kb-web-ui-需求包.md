## 后续需求：服务端配置管理与安装分发（2026-10-29）

### 需求描述

面向用户本人单人高效运维，提供自己的 KB 服务端与管理后台，集中完成 KB 配置、实例与凭据管理、同步状态查看、门禁和审计管理。知识内容的仓库、编辑、PR/MR、评审、合并与历史直接复用 Gitea/GitLab，不重复建设复杂的内容管理平台。

**管理后台同时作为 omo 的自有安装入口，直接提供可下载的安装脚本和可复制的安装命令。用户在目标机器主动拉取并执行脚本，完成安装，并利用后台提供的接入信息完成 KB 接入。** 用户不必再到 GitHub 查找安装脚本或手工拼装安装参数。

这里的「远程安装脚本」是**由自己的服务端分发、在目标机器执行**，不是管理后台通过 SSH 登录目标主机代装。此前提出的主机 SSH 凭据托管、后台远程执行安装任务不属于本需求。

需求依据：2026-10-29 会话，用户确认「目前只要能满足我一个人高效运维即可」「kb 内容管理平台直接使用 Gitea/GitLab」；随后明确纠正「希望我们自己的管理后台直接提供远程安装脚本」，并确认按此理解修正需求描述。

### 范围与责任

| 编号 | 范围 | 要求 |
|---|---|---|
| REQ-M01 | 配置与管理 | 后台提供 KB 配置、实例、凭据、同步、门禁与审计的统一管理入口，明确显示配置与操作是否生效；管理面验收见 AC-M01–AC-M07 |
| REQ-M02 | 内容管理 | 复用 Gitea/GitLab 的仓库、内容编辑、评审与历史能力；后台提供关联入口，不另建内容存储和评审流程。**首期例外：GitLab 只做内容同步，建号/授权/门禁自动化后续适配；需求包显式记录此例外，UI 不得伪装已支持** |
| REQ-I01 | 安装分发 | 自有后台直接提供安装脚本及对应命令，不仅放置跳转 GitHub 安装说明的链接 |
| REQ-I02 | 执行主体 | 用户在目标机器主动执行；后台无需目标主机的 SSH 登录凭据，不主动建立远程执行连接 |
| REQ-I03 | 安装接入 | 从后台获取必要的 KB 服务地址与接入信息，安装流程衔接 KB 接入，避免新装实例逐台手工补写同一组配置。**首期范围仅新装实例；已有实例通过显式 `omo kb` 刷新，不做后台自动下发** |
| REQ-I04 | 结果反馈 | 区分「脚本已获取」「软件已安装」「KB 已接入」；下载成功不得算安装成功，登记存在不得算实例在线 |
| REQ-I05 | TLS 信任 | 服务端自签证书作为 CA 交付，安装命令同时携带 **CA 证书 + 公钥 SPKI pin**；现代 curl 用 `--cacert` + `--pinnedpubkey` 双锚；禁止 `-k`/关闭证书校验；证书轮换需重新生成安装命令 |
| REQ-I06 | 制品托管 | 安装制品由服务端预缓存/上传或代理，目标机只访问自己的控制面；服务端必须本地重算并保存哈希，不信任上游元数据 |
| REQ-I07 | 目标平台 | 现代 curl ≥7.55 走 `--cacert`+`--pinnedpubkey`+`--header @file`；el7 类 curl 7.29–7.54 走 `--cacert` + openssl SPKI pin 校验 + `--config` 头文件（实现前 el7 真机探针）；curl <7.29 明确失败并给升级指引 |

### 典型操作流程

**进入自有后台 → 配置或检查 KB 服务 → 获取安装脚本/命令 → 用户在目标机器执行 → 安装与 KB 接入自证 → 回到后台管理实例。**

常规新增实例的安装操作收敛为「后台获取命令」「目标机器执行」两个位置，不增加人工前往 GitHub 查找安装入口的步骤。只在后台查看或获取脚本不会触发目标机器上的变更。

### 明确不做

- 不建设 SSH 远程代装、目标主机 SSH 凭据托管或后台任意命令执行能力。
- 不扩成通用应用部署平台，也不把 KB 配置管理扩大为对 omo 模型、SSH 和本地运维授权策略的远程控制。
- 不以多租户、复杂多人协作和角色体系作为首期前置条件；单人使用不意味着取消认证。
- 不因自有安装入口而要求迁移 GitHub 源码仓库或重建 CI/CD。
- 不把安装脚本分发等同于所有安装包、运行时和依赖都必须自建托管；**制品来源已由 REQ-I06 拍板为服务端缓存/上传或代理**，容量/清理/带宽仍由设计评估，不再作为未决方向。

### 安装分发验收标准（待实现后验证）

| 编号 | 前提与操作 | 预期结果 |
|---|---|---|
| AC-I01 | 在自有后台获取安装脚本与命令 | 脚本由自己的服务端提供；用户无需另行查找 GitHub 安装说明或手工拼装服务地址与接入参数 |
| AC-I02 | 仅在后台查看或下载安装脚本 | 后台不连接目标主机，不触发远程安装或重启，不要求输入目标主机 SSH 凭据 |
| AC-I03 | 在受支持的干净目标环境执行命令，下载来源和 KB 服务可达且接入信息有效 | 软件安装完成，KB 接入自证成功；无需手工复制服务端管理员凭据或编辑实例 KB 配置 |
| AC-I04 | 脚本下载失败、安装包不可达或环境不受支持 | 明确报错并停止对应步骤，不执行残留旧脚本、不伪报成功；提示可行动的修正或重试方式 |
| AC-I05 | 软件安装成功，但 KB 服务不可达或接入凭据无效 | 明确显示「已安装、接入失败」与原因，不把两者合并报告为成功 |
| AC-I06 | 目标机器已有安装、配置及知识数据 | 无升级意图时拒绝静默覆盖并提示升级命令；升级时保留 `~/.omo/home` 与 KB 凭据；重复执行/升级规则由安装脚本显式检查，不依赖 `install.sh` 现有行为 |
| AC-I07 | 检查脚本、命令、响应和日志 | 不包含可复用的服务端管理员秘密；操作记录区分脚本获取与实际接入结果，不凭下载次数推断在线状态 |
| AC-I08 | 从后台进入知识内容编辑或评审 | 使用关联 Gitea/GitLab 的既有能力，不产生独立的内容存储或第二套评审流程 |
| AC-I09 | 安装命令使用服务端自签 CA + 公钥 SPKI pin；现代 curl 执行 | `--cacert`+`--pinnedpubkey` 成功；错误 pin 失败；不提供 `-k` 回退；证书轮换后旧命令失效 |
| AC-I10 | 服务端缓存/上传或代理制品后，检查服务端保存的哈希与目标机下载校验 | 服务端本地重算 sha256（含代理路径），不信任上游清单；缓存被篡改或上游哈希被替换时，目标机拒绝安装 |
| AC-I12 | 现代 curl（≥7.55）安装 | `--cacert`+`--pinnedpubkey`+`--header @file` 全链成功；pin-only（无 cacert）明确失败，不误报成功 |
| AC-I13 | el7 类 curl（7.29–7.54）安装 | `openssl` 校验 CA SPKI pin + `curl --cacert` + `--config` 头文件成功；curl <7.29 或缺 openssl 时明确失败并给升级指引 |

### 首期例外与前提

- **GitLab 例外**：首期只保证 GitLab 内容同步（仓库/分支/PR/评审/历史）；建号、授权、门禁自动化不在首期，UI 明示「内容同步可用，管理自动化未启用」。
- **配置刷新范围**：REQ-I03 只覆盖新装实例；已有实例通过显式 `omo kb` 命令刷新，后台不推送、不远程改本地配置。
- **TLS 信任**：服务端自签 CA + 证书公钥 SPKI pin；`--cacert`+`--pinnedpubkey` 双锚；不使用 `-k`；证书轮换需重新生成安装命令。
- **制品托管**：服务端缓存/上传或代理；目标机只访问控制面；服务端本地重算哈希。
- **管理面入口**：管理 API 默认绑定 loopback，经 yufu 反代或 SSH 隧道访问；不把 `X-Auth-Username` 头存当认证。
- **假设**：目标机可访问控制面；控制面具备制品缓存容量；Gitea 管理 API 可用于建号/授权；GitLab 仅内容同步；yufu 或本机隧道提供管理入口。
- **本地账户模型**：管理监听 loopback 端口对本机所有 UID 可达，不是“仅同 UID”；首期按单用户服务机假设，若同机多用户需防火墙、独立主机或 UNIX socket。
- **阻断项**：Gitea 分支保护/webhook API 能力需实现前探针确认；管理面入口加固未完成不得上线签发类 API；TLS 路径在目标 curl 版本不支持时明确失败，不降级到 `-k`。

### 设计阶段自行核实的事项

- 如何复用现有安装链路，保证脚本与安装版本一致、下载完整性可验证。
- 制品来源已拍板为服务端缓存/上传或代理；设计阶段仍需评估容量、清理和带宽，不把“已拍板”当成“已落容量方案”。
- 接入信息的安全交付与有效期、安装失败后的续接方式，以及已有实例的重复安装与升级保护。
- 管理和脚本下载的认证边界、首次初始化与恢复路径；不以开放无认证管理入口或关闭证书验证换取便利。
- Gitea 管理 API 需实现前探针；GitLab 首期仅内容同步，不把普通 git 同步等同于完整管理 API。

以上技术取舍依据现有实现与合理默认值独立完成，仅实质改变已确认范围或无法推断的关键决策才请求确认。本节仅更新需求，不代表设计完成、实施授权或生产变更授权。
